  - Root cause of "Integration Status: Disabled": `laravel-crm/.env` had no `JUSTCALL_ENABLED` key, and `config/justcall.php` defaults it to `false`. Credentials being configured never implied enabled. Set `JUSTCALL_ENABLED=true` in the local `.env` (dev environment) since credentials are present; `.env.example` keeps the safe `false` default for new environments.
  - Verified current official JustCall docs (`developer.justcall.io/reference/authentication`): required header is `Authorization: api_key:api_secret` (raw, colon-joined, not base64). Default `auth_mode` changed from `basic` to `raw` in `config/justcall.php`, `.env`, and `.env.example` to match official docs. A real API call showed JustCall's `/v2.1/users` endpoint currently accepts both `raw` and base64 `basic` auth, so `basic` was kept as a supported legacy option, not removed.
  - Added real CONNECTED/CONFIGURED/CONNECTION FAILED/DISABLED integration-status logic (`JustCallClient::status()`), driven by the cached result of the last real `testConnection()` call (never inferred from credential presence alone). Displayed on the JustCall Settings page with last-tested time.
  - Real server-side connection test executed against `https://api.justcall.io/v2.1/users` with configured credentials: HTTP 200, `JustCall connection successful.` (see T36 entry in FINAL RESPONSE below for full details). No secrets were logged or printed.
  - Click-to-Call audit: fully implemented end-to-end (RBAC-gated button on Lead/Customer/Contact -> `JustCallClickToCallController` -> `JustCallClickToCallService` -> CRM user/JustCall agent mapping check -> phone normalization -> dialer popup URL -> webhook -> `CallLogUpsertService`). Method used is the JustCall Dialer Popup (Option B), not the embedded Dialer SDK. Fixed a UX gap where the popup redirect replaced the CRM tab; the click-to-call forms now open the dialer in a new tab (`target="_blank"`) so the agent stays in the CRM.
  - Seamless JustCall login requirement investigated against the actual bundled `justcall-dialer-sdk` client (used by the separate legacy PHP app) and JustCall's public docs: the SDK only exposes `onLogin`/`onLogout`/`isLoggedIn`/`dialNumber` (postMessage/iframe based); there is no documented `authenticate`/`setToken`/`setUser` method for a backend-issued session token. Conclusion: **seamless first-time JustCall login via the SDK is BLOCKED/LIMITED by JustCall's own SDK capabilities**, not a CRM implementation gap. A logged-in JustCall browser session is reused automatically (same-origin cookies) once the agent has logged in once; no code changes could safely remove that first login without violating the security restriction against storing/forwarding agent passwords.
